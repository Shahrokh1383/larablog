# Categories Module Documentation

## 1. Quick Reference for Developers & AI

**Module purpose:** Flat (non‑hierarchical) category taxonomy attached to posts via a many‑to‑many pivot.

### 1.1 At a Glance

- **Table:** `categories` (id, name, slug, description, timestamps)  
- **Pivot:** `category_post` (post_id, category_id) – CASCADE on both FKs  
- **Model:** `App\Models\Category` – uses Spatie Sluggable (slug auto‑generated from name **only at creation**)  
- **Admin controller:** `App\Http\Controllers\Admin\CategoryAdminController` – full CRUD, restricted to `Admin` role  
- **Authorization:** Multi‑layer – `auth` + `role:Admin` middleware, Policy checks (permission `manage categories`), plus a hard controller check preventing deletion of categories with live (non‑soft‑deleted) posts.  
- **Slug behaviour:**  
  - On **create**: slug is auto‑generated by Spatie if the slug field is empty.  
  - On **update**: Spatie does **not** regenerate the slug, but the Form Request’s `prepareForValidation()` will **always** generate a fresh slug from `name` if the slug field is submitted empty (whether or not the name was changed).  
    - **To keep slugs stable, always send the current slug value in update forms.**  
- **Deletion rule:** A category **cannot** be deleted if ANY non‑soft‑deleted post is attached. This is enforced both in the Policy and in the controller.

### 1.2 Decision Tree for Common Tasks

```
Need to create a category?
├─ Are you an Admin? → Yes → Use POST /admin/categories (form data: name, slug (optional), description (optional)).
│   └─ If slug is empty, it will be auto‑generated from name.
└─ No → Not allowed (403).

Need to update a category?
├─ Are you an Admin? → Yes → Use PUT/PATCH /admin/categories/{id}
│   ├─ Want to keep slug unchanged? → Always send the current slug value in the request.
│   └─ Want to change slug? → Send new slug (must match regex /^[a-z0-9-]+$/).
└─ No → Not allowed.

Need to delete a category?
├─ Are you an Admin? → Yes → Check if category has any live posts (not soft‑deleted).
│   ├─ Has live posts → Deletion blocked (flash error).
│   └─ No live posts → Deletion allowed.
└─ No → Not allowed.
```

### 1.3 Admin Endpoints Summary

| Method     | URI                                     | Route Binding | Access | Description                                                         |
|------------|-----------------------------------------|---------------|--------|---------------------------------------------------------------------|
| GET        | `/admin/categories`                     | –             | Admin  | Paginated list (includes soft‑deleted post count).                  |
| GET        | `/admin/categories/create`              | –             | Admin  | Show creation form.                                                 |
| POST       | `/admin/categories`                     | –             | Admin  | Store new category.                                                 |
| GET        | `/admin/categories/{category}/edit`     | id            | Admin  | Edit form.                                                          |
| PUT/PATCH  | `/admin/categories/{category}`          | id            | Admin  | Update category.                                                    |
| DELETE     | `/admin/categories/{category}`          | id            | Admin  | Delete category (fails if live posts exist).                        |

### 1.4 Public Endpoint

| GET | `/categories/{category:slug}` | slug | Public | Show published posts in that category (12 per page). |

### 1.5 Authorization Flow (Simplified)

1. All admin routes require `auth` middleware → must be logged in.  
2. Then `role:Admin` middleware → only users with the Spatie role `Admin` pass.  
3. Controller actions additionally call `Gate::authorize()` which uses the `CategoryPolicy`.  
4. A global `Gate::before` allows `Admin` users for **any** ability, so admins bypass the policy entirely.  
5. The delete action has an **extra hard check** in the controller: `$category->posts()->exists()` – stops even admins.

## 2. Overview

The Categories module provides a flat, non‑hierarchical taxonomy that can be assigned to blog posts.  
Key characteristics:

- No parent‑child relationships (flat list).  
- Many‑to‑many relationship with `Post`.  
- Slug auto‑generation on creation via Spatie Sluggable.  
- Deletion is forbidden if any **non‑soft‑deleted** posts are linked.  
- Categories are permanently deleted (hard delete).  
- Pivot table (`category_post`) uses `ON DELETE CASCADE` – deleting a category removes its pivot rows; deleting a post (hard delete) also removes its pivot rows. Soft‑deleting a post leaves pivot rows untouched.

## 4. Database Schema

### 4.1 `categories` Table

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `BIGINT UNSIGNED` | No | Auto‑increment | Primary key |
| `name` | `VARCHAR(100)` | No | – | Unique; user‑friendly label |
| `slug` | `VARCHAR(100)` | No | – | Unique; URL‑safe identifier |
| `description` | `TEXT` | Yes | `NULL` | Optional description |
| `created_at` | `TIMESTAMP` | Yes | `NULL` | Set by Eloquent |
| `updated_at` | `TIMESTAMP` | Yes | `NULL` | Set by Eloquent |

**Indexes:**  
- `UNIQUE KEY categories_name_unique (name)`  
- `UNIQUE KEY categories_slug_unique (slug)`  

> ⚠️ Timestamp columns are nullable at the database level (Laravel’s default). In normal operation Eloquent always fills them.

### 4.2 `category_post` Pivot Table

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `BIGINT UNSIGNED` | No | Auto‑increment | Primary key |
| `post_id` | `BIGINT UNSIGNED` | No | – | FK → `posts.id` ON DELETE CASCADE |
| `category_id` | `BIGINT UNSIGNED` | No | – | FK → `categories.id` ON DELETE CASCADE |
| `created_at` | `TIMESTAMP` | Yes | `NULL` | Pivot timestamp (set because `withTimestamps()` is used) |
| `updated_at` | `TIMESTAMP` | Yes | `NULL` | Pivot timestamp |

**Constraints:**  
- `UNIQUE(post_id, category_id)` – prevents duplicates.  
- `FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE`  
- `FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE CASCADE`

**Cascade behaviour:**  
- Deleting a category → all its pivot rows removed; posts untouched.  
- Hard‑deleting a post → all its pivot rows removed; categories untouched.  
- Soft‑deleting a post → pivot rows persist (they are NOT soft‑deleted).

## 5. Models

### 5.1 Category (`App\Models\Category`)

| Property | Value |
|----------|-------|
| Table | `categories` |
| Primary Key | `id` |
| Fillable | `['name', 'slug', 'description']` |
| Traits | `HasFactory`, `HasSlug` (Spatie) |
| Route Key Name | Not overridden → defaults to `id` (used in admin routes). Public route explicitly uses `{category:slug}`. |

#### Slug Configuration

```php
public function getSlugOptions(): SlugOptions
{
    return SlugOptions::create()
        ->generateSlugsFrom('name')
        ->saveSlugsTo('slug')
        ->doNotGenerateSlugsOnUpdate(); // Spatie will NOT update slug on model->update()
}
```

**Important behaviour summary:**

- **On creation:** If `slug` is not provided, Spatie generates a unique slug from `name` before saving.  
- **On model update (`$category->update(...)`):** Spatie does **nothing**. However, because `slug` is fillable, it can be changed by the application. The `CategoryRequest` may generate a new slug before validation (see §7.3).  
- **Critical:** The Form Request’s `prepareForValidation()` runs **on every update request**. If the `slug` field is empty in the request, it generates a new slug from the current `name`, regardless of whether the name changed. Always include the existing slug value to keep it stable.

#### Relationships

```php
public function posts(): BelongsToMany
{
    return $this->belongsToMany(Post::class)->withTimestamps();
}
```

- Pivot table: `category_post`.  
- The relationship **excludes soft‑deleted posts** by default (thanks to `Post`’s `SoftDeletes` scope). Use `$category->posts()->withTrashed()` to include them.  
- `withTimestamps()` ensures `created_at` and `updated_at` are set on pivot records.

#### Accessor: `posts_count` (live posts only)

```php
public function getPostsCountAttribute(): int
{
    return $this->posts()->count(); // excludes soft-deleted posts
}
```

**Note:** This accessor is **not used** in the admin panel. The admin index overrides the count to include trashed posts (business decision: admins need to see total associations).

### 5.2 Post (`App\Models\Post`) – Relevant Parts

```php
public function categories(): BelongsToMany
{
    return $this->belongsToMany(Category::class)->withTimestamps();
}
```

**Scopes useful for category filtering:**

- `scopePublished($query)` – filters `status = 'published'` and `published_at <= now()`.  
- `scopeInCategory($query, string $categorySlug)` – loads posts belonging to a category with the given slug.

## 6. Authorization & Permissions

### 6.1 Complete Authorization Chain

Every admin request passes through the following layers (in order):

1. **auth middleware** – user must be logged in.  
2. **role:Admin middleware** – only users with `Admin` role pass.  
3. **Global `Gate::before`** (in `AuthServiceProvider`):  
   ```php
   Gate::before(function ($user, $ability) {
       return $user->hasRole('Admin') ? true : null;
   });
   ```  
   If the user is an Admin, all subsequent gate/policy checks are skipped and `true` is returned immediately. Therefore, admins bypass all policy logic.  
4. **Controller `Gate::authorize()` / Form Request `authorize()`**: These calls map to policy methods (e.g., `Gate::authorize('update', $category)` → `CategoryPolicy@update`).  
   - With the current architecture, non‑Admin users cannot reach this point because the `role:Admin` middleware blocks them earlier. If that middleware were ever removed, the policy methods would be executed. They require the Spatie permission `manage categories`.  
5. **Hard check in `destroy` method** (only for delete): Even after passing policy authorization, the controller checks `$category->posts()->exists()` and blocks deletion if live posts are linked. This is an extra safety net.

> ⚠️ **Important**: The route group also includes `->middleware('can:manage categories')`, but no gate/ability named `manage categories` is defined. Because of the global `Gate::before`, admins pass anyway. This middleware has no effect under the current architecture; it can be removed or formally defined (see Known Issues).

**Authorization Flow Diagram (Textual):**

```
Request
  │
  ├─ auth?
  │    └─ No → 401 Unauthenticated
  │
  ├─ role:Admin?
  │    └─ No → 403 Forbidden
  │
  ├─ Gate::before
  │    └─ Admin? → true (skip policy)
  │
  ├─ Gate::authorize('action', ...) or FormRequest::authorize()
  │    ├─ Admin → true (already true from before)
  │    └─ Non‑Admin (never reached due to role middleware)
  │         └─ Policy check: hasPermissionTo('manage categories')?
  │              ├─ Yes → allowed
  │              └─ No → 403
  │
  ├─ [Only for destroy] $category->posts()->exists()?
  │    ├─ Yes → redirect back with error
  │    └─ No → proceed (delete)
```

### 6.2 CategoryPolicy (`App\Policies\CategoryPolicy`)

| Method | Logic |
|--------|-------|
| `viewAny` | `$user->hasPermissionTo('manage categories')` |
| `view` | `return true` (public) |
| `create` | `$user->hasPermissionTo('manage categories')` |
| `update` | `$user->hasPermissionTo('manage categories')` |
| `delete` | 1) If Admin → `true`. 2) If category has live posts → `false`. 3) Else → `hasPermissionTo('manage categories')`. |

> **Note:** The explicit Admin check inside `delete` is redundant because of `Gate::before`, but it is harmless and serves as documentation of intent.

### 6.3 Effective Access Matrix

| Action | Admin | Editor (with `manage categories`) | Reason |
|--------|-------|-----------------------------------|--------|
| View admin index / create form | ✅ | ❌ | `role:Admin` middleware |
| Store (create) | ✅ | ❌ | Route middleware + `authorize()` bug (see §11.1) |
| Edit / Update | ✅ | ❌ | `role:Admin` middleware |
| Delete (has live posts) | ❌ | ❌ | Controller hard check |
| Delete (zero live posts) | ✅ | ❌ | `role:Admin` middleware |

## 7. Admin Controller

**Class:** `App\Http\Controllers\Admin\CategoryAdminController`  
**Base URL:** `/admin/categories`  
**Model binding:** `{category}` resolved by `id` (default).

### 7.1 `index()` – `GET /admin/categories`

- Authorization: `Gate::authorize('viewAny', Category::class)`  
- Query:  
  ```php
  Category::withCount(['posts' => fn($q) => $q->withTrashed()])
      ->latest()
      ->paginate(15);
  ```
  The `posts_count` includes soft‑deleted posts so that admins see the total number of attached posts, even if trashed.  
- View: `admin.categories.index`

### 7.2 `create()` – `GET /admin/categories/create`

- `Gate::authorize('create', Category::class)`  
- Returns empty form view.

### 7.3 `store(CategoryRequest $request)` – `POST /admin/categories`

- Authorization inside `CategoryRequest`.  
- Wrapped in `DB::transaction`:  
  1. `Category::create($request->getCategoryData())`  
  2. Log info: `Category created` with `category_id`, `name`, `created_by`  
- Redirect back with success flash: `"Category '{$category->name}' created successfully!"`

**Example request (form data):**

```
POST /admin/categories
name=Web Development
description=All about web
slug=
```

**Behaviour:** slug auto‑generated as `web-development`.

### 7.4 `edit(Category $category)` – `GET /admin/categories/{category}/edit`

- `Gate::authorize('update', $category)`  
- Returns edit view with the existing model.

### 7.5 `update(CategoryRequest $request, Category $category)` – `PUT/PATCH /admin/categories/{category}`

- Authorization via FormRequest.  
- Wrapped in `DB::transaction`:  
  1. Save old name.  
  2. `$category->update($request->getCategoryData())`  
  3. Log info: `Category updated` with old/new name, `updated_by`  
- Redirect with success.

**Example request (update name, keep slug):**

```
PUT /admin/categories/5
name=Full-Stack Development
slug=web-development
description=Updated description
```

**Example request (update name, empty slug → new slug):**

```
PUT /admin/categories/5
name=Full-Stack Engineering
slug=
description=...
```

**Result:** slug becomes `full-stack-engineering`.

### 7.6 `destroy(Category $category)` – `DELETE /admin/categories/{category}`

- **Form request NOT used** for this action; authorization is done directly.  
- Steps:  
  1. `Gate::authorize('delete', $category)` – Policy check.  
  2. **Controller hard check:**  
     ```php
     if ($category->posts()->exists()) {
         return back()->with('error', "Cannot delete category '{$category->name}' because it has associated posts.");
     }
     ```  
     This check uses `posts()->exists()`, which **excludes soft‑deleted posts**. So if only soft‑deleted posts are attached, deletion proceeds.  
  3. `DB::transaction`: delete category (cascade pivot), log with `name`, `deleted_by`.  
  4. Redirect with success flash.

## 8. Form Request – `CategoryRequest`

**Used by:** `store` and `update` actions.

### 8.1 Authorization

```php
public function authorize(): bool
{
    return match($this->method()) {
        'POST'          => Gate::allows('create categories'),
        'PUT', 'PATCH'  => Gate::allows('update', $this->route('category')),
        'DELETE'        => Gate::allows('delete', $this->route('category')),
        default         => false,
    };
}
```

- **`POST` (store)**: uses a non‑existent gate `create categories`. The only reason it works is the global `Gate::before` that returns `true` for Admins. Non‑Admins are already blocked by role middleware, so the bug is latent.  
- **`PUT/PATCH`**: correctly checks `update` against the policy.  
- **`DELETE`**: present but never invoked; dead code (controller does not inject `CategoryRequest` for deletion).

### 8.2 Validation Rules

| Field | Rules |
|-------|-------|
| `name` | `required`, `string`, `min:2`, `max:100`, `unique:categories,name,{$categoryId}` |
| `slug` | `nullable`, `string`, `min:2`, `max:100`, `unique:categories,slug,{$categoryId}`, `regex:/^[a-z0-9-]+$/` |
| `description` | `nullable`, `string`, `max:1000` |

On update, the unique rules ignore the current category ID.

### 8.3 Slug Auto‑generation (`prepareForValidation`)

```php
if (!$this->slug && $this->name) {
    $this->merge(['slug' => Str::slug($this->name)]);
}
```

This runs **on both create and update**.  
**Decision table:**

| Scenario | Name | Slug in request | Final slug | Notes |
|----------|------|-----------------|------------|-------|
| Create – no slug | "Laravel" | "" (empty) | `laravel` | Auto‑generated |
| Update – name unchanged | "Laravel" | "" (empty) | `laravel` | Same as before (no effective change) |
| Update – name changed | "Livewire" | "" (empty) | `livewire` | **New slug!** Old URLs break |
| Update – any | any | provided (valid) | provided value | – |

> **Best practice:** To keep slugs stable after creation, always include the existing slug value in the edit form submission. The front‑end should pre‑fill the slug input with the current value.

### 8.4 Data Output

`getCategoryData()` returns `$this->validated()` → `['name', 'slug', 'description']`. This is passed to `Category::create()` or `->update()`.

## 9. Pivot Table Behaviour

| Action on Post | Effect on `category_post` |
|----------------|---------------------------|
| Hard delete | Pivot rows with that `post_id` deleted (CASCADE) |
| Soft delete | Pivot rows **unchanged** |
| Restore (from soft delete) | Links become active again automatically |
| Force delete | Pivot rows deleted (CASCADE via FK) |

When a category is deleted, all its pivot rows are removed by FK cascade. Posts remain untouched.

## 11. Logging

All write operations log at `info` level using `Illuminate\Support\Facades\Log`.

| Event | Message | Context keys |
|-------|---------|--------------|
| Created | `Category created` | `category_id`, `name`, `created_by` |
| Updated | `Category updated` | `category_id`, `old_name`, `new_name`, `updated_by` |
| Deleted | `Category deleted` | `category_id`, `name`, `deleted_by` |

**Important:** Log statements are executed inside `DB::transaction` blocks. However, application logs (file, etc.) are **not** part of the database transaction. If the transaction fails and rolls back, any log entry written before the rollback **will still persist**. This can lead to “false positive” log entries (e.g., a log saying “Category created” even though the DB insert was rolled back). In the current implementation this is acceptable because failures are unlikely after validation, but be aware of this when troubleshooting.

## 13. Performance Considerations

- **Indexing**: The `categories` table has unique indexes on `name` and `slug` – good for lookups and the public route `where slug = ?`.  
- **Pagination**: Admin index uses `paginate(15)`, public filter uses `paginate(12)` – safe for large datasets.  
- **Eager loading**: The public filter route eager loads `author`, `categories`, `tags` – avoid N+1.  
- **`withCount` in admin index**: Uses a subquery with `withTrashed()`, which is efficient as it’s a single aggregate.  
- **Pivot timestamps**: Enabled via `withTimestamps()`. On large pivot tables, this may impact write performance slightly but is acceptable.

## 14. Troubleshooting / FAQ

### Q1: Why can’t an Editor (even with `manage categories` permission) create a category?

**A:** The admin routes are protected by `role:Admin` middleware, which explicitly blocks Editors. Even if the middleware were removed, the `CategoryRequest::authorize()` for `POST` uses an undefined gate, so Editors would still get a 403. To enable Editor access, you’d need to:
- Change the route middleware to `role:Admin|Editor` or a permission‑based gate, and
- Fix the `authorize()` method to use `Gate::allows('create', Category::class)`.

### Q2: Why does the slug change even though `doNotGenerateSlugsOnUpdate()` is set?

**A:** Spatie Sluggable does not regenerate the slug on update, but the `CategoryRequest`’s `prepareForValidation()` method manually creates a new slug from the current name if the slug field is empty. This happens regardless of whether the name changed. To prevent this, always pass the current slug value in the update form.

### Q3: I deleted a post (soft‑delete) and then tried to delete its category, but it still fails.

**A:** The check `$category->posts()->exists()` uses the default relationship, which excludes soft‑deleted posts only if the Post model uses `SoftDeletes`. In this project, `Post` **does** use `SoftDeletes`, so `exists()` should return `false` when all posts are soft‑deleted. Verify that you actually soft‑deleted the post (not hard‑deleted, which cascades and removes the pivot). If you still face issues, check for any global scopes overriding the soft‑delete behaviour.

### Q4: Why does the admin index show a count of posts that includes trashed ones?

**A:** It was a deliberate product decision. The admin panel is meant to show the total number of associations, including trashed posts, so that category managers are aware of all links (e.g., before deletion). The model accessor `$category->posts_count` still returns only live posts for public or API usage.

## 15. Known Issues & Gotchas

1. **Store authorization uses undefined gate**  
   - `CategoryRequest::authorize()` for `POST` calls `Gate::allows('create categories')`, which does not exist. Works only because of `Gate::before` and the `role:Admin` middleware.  
   - **Fix:** Change to `Gate::allows('create', Category::class)`.

2. **`can:manage categories` middleware has no effect**  
   - No gate named `manage categories` is defined. If you ever remove `role:Admin`, this middleware won’t block anyone.  
   - **Fix:** Either define the gate in `AuthServiceProvider` or remove the middleware.

3. **Slug instability on update**  
   - If the admin changes the name (or even just clears the slug field) and leaves slug empty, a new slug is generated. This can break existing bookmarks/SEO.  
   - **Mitigation:** Ensure the edit form **always pre‑fills the slug field**. You may also consider making slug read‑only after creation by removing it from `$fillable` or from the auto‑generation logic on update.

4. **Dead code in `authorize()`**  
   - The `DELETE` branch is never triggered because the controller does not inject `CategoryRequest` for the destroy action. It’s harmless but could confuse developers.  
   - **Recommendation:** Remove the `DELETE` branch or add a comment explaining its presence.

5. **Log persistence despite transaction rollback**  
   - Log entries written inside `DB::transaction` will survive even if the transaction is rolled back. This can create “phantom” log entries in rare failure scenarios. Keep this in mind when correlating logs with actual data state.

## 17. Extending the Module

- **Adding hierarchy:** Add a nullable `parent_id` FK to `categories`. Consider using a nested‑set package like `kalnoy/nestedset` for efficient tree queries. Update deletion policies accordingly.  
- **Category‑specific settings:** Add a `JSON` column, update `$fillable`, and adjust validation.
