# Authentication Module

## Overview

The Authentication module governs all identity‑based flows in LaraBlog: login, registration, password reset, and logout. It is built on Laravel’s native session‑based authentication, using the `web` guard with the `users` Eloquent provider (`App\Models\User`). The module integrates deeply with Spatie’s role/permission system (role assignment at registration) and a custom ban system that prevents banned users from maintaining an active session. Every route is protected either by the `guest` middleware (unauthenticated users only) or the `auth` middleware (authenticated users only). Laravel’s `Registered` and `PasswordReset` events are fired, leaving room for future listeners.

**Important:** Several pieces of functionality referenced in the code rely on database columns that **do not exist** in the current migrations. These gaps are documented below and must be resolved before the code can run without errors.

## Models

### `User` (`App\Models\User`)

- **Table:** `users`
- **Primary Key:** `id`
- **Fillable:** `name`, `email`, `password`, `avatar`, `bio`, `social_links`, `email_verified_at`, `banned_at`, `banned_by`, `ban_reason`
  - **Warning:** `last_login_at` and `updated_by` are **not** fillable, yet the code attempts to mass‑assign `last_login_at`. This will cause a runtime error (see Technical Debt).
- **Guarded:** Not explicitly set; uses `$fillable` so all other attributes are guarded.
- **Hidden:** `password`, `remember_token`
- **Casts:**
  - `email_verified_at` → `datetime`
  - `password` → `hashed` (Laravel 10+ automatic hashing)
  - `social_links` → `array`
  - `banned_at` → `datetime`
- **Traits:** `HasApiTokens`, `HasFactory`, `Notifiable`, `HasRoles` (Spatie), `SoftDeletes`
- **Relationships:**
  - `posts()` → `hasMany(Post::class, 'user_id')` – Posts authored by the user.
  - `bannedBy()` → `belongsTo(User::class, 'banned_by')` – The admin who banned this user.
  - `updater()` → `belongsTo(User::class, 'updated_by')` – The user who last updated this profile. **⚠️ Requires missing `updated_by` column.**
- **Accessors / Custom Attributes:**
  - `getAvatarUrlAttribute()`: Returns a Gravatar fallback (based on email MD5) if `avatar` is empty or the file is missing from storage.
  - `getPublishedPostsCountAttribute()`: Count of the user’s published posts.
  - `getLastActivityAttribute()`: Returns a human‑readable time difference of the most recent login (`last_login_at`) or latest post creation. **⚠️ Uses the non‑existent `last_login_at` column.**
- **Role Checks:**
  - `isAdmin()` → `hasRole('Admin')`
  - `isEditor()` → `hasRole('Editor')`
  - `isAuthor()` → `hasRole('Author')`
- **Ban System:**
  - `isBanned()` → `true` if `banned_at !== null`
  - Scopes: `scopeNotBanned($query)`, `scopeBanned($query)`
- **Model Events (`boot()`):**
  - `deleting`: When a user is deleted, their posts are soft‑deleted (or force‑deleted if the user is force‑deleting). This cascades to keep the database consistent.
  - `restoring`: Restores the user’s soft‑deleted posts.
- **Other Methods:**
  - `unreadNotificationsCount()` → count of unread database notifications (used for UI).

## Controllers

### `LoginController` (`App\Http\Controllers\Auth\LoginController`)

#### `showLoginForm()`
- **Route:** `GET /login` (name: `login`)
- **Middleware:** `guest`
- **Returns:** `view('auth.login')`

#### `login(LoginRequest $request)`
- **Route:** `POST /login`
- **Middleware:** `guest`
- **Validation:** Handled by `LoginRequest`.
- **Processing:**
  1. Attempt authentication with `email`, `password`, and the `remember` boolean.
  2. **On success:**
     - Regenerate the session and CSRF token.
     - Check if the authenticated user is banned via `$user->isBanned()`. If banned, immediately log out, invalidate the session, and redirect back with an error message. This ensures no active session remains for banned users.
     - If not banned, attempt to update `last_login_at`.
       - **Current issue:** The call `$user->update(['last_login_at' => now()])` fails because the column does not exist (QueryException). Even if the column existed, mass‑assignment would fail unless the attribute is made fillable or `forceFill()` is used. (See Technical Debt.)
     - Redirect to the intended URL (default `dashboard`) with a success flash message.
  3. **On failure:**
     - Log a warning containing the email, IP, and user agent.
     - Throw a `ValidationException` with a generic “credentials do not match” message.
- **Returns:** Redirect.

#### `logout(Request $request)`
- **Route:** `POST /logout` (name: `logout`)
- **Middleware:** `auth`
- **Processing:**
  1. Capture user details for logging.
  2. Call `Auth::logout()`.
  3. Invalidate the session and regenerate the CSRF token.
  4. Log the logout event.
  5. Redirect to the home page (`/`) with a success flash message.
- **Returns:** Redirect.

### `RegisterController` (`App\Http\Controllers\Auth\RegisterController`)

#### `showRegistrationForm()`
- **Route:** `GET /register` (name: `register`)
- **Middleware:** `guest`
- **Returns:** `view('auth.register')`

#### `register(RegisterRequest $request)`
- **Route:** `POST /register`
- **Middleware:** `guest`
- **Validation:** Handled by `RegisterRequest`.
- **Processing:**
  1. Obtain validated user data from `$request->getUserData()`, which already contains a hashed password and `email_verified_at` set to `now()`.
  2. Merge additional defaults: a random `remember_token`, `bio` = 'New member at LaraBlog', empty `social_links`, and `avatar = null`.
  3. Create the user record via `User::create(...)`.
  4. Assign the ‘User’ role using Spatie’s `$user->assignRole('User')`.
  5. Fire the `Registered` event.
  6. Log the registration.
  7. Automatically log in the new user.
  8. Redirect to the `dashboard` route with a welcome message.
- **Returns:** Redirect.

**Design Decision:** The app auto‑verifies the email by setting `email_verified_at` immediately, bypassing the standard email verification flow. This is intentional for the current scope of the platform.

### `ForgotPasswordController` (`App\Http\Controllers\Auth\ForgotPasswordController`)

#### `showLinkRequestForm()`
- **Route:** `GET /password/reset` (name: `password.request`)
- **Middleware:** `guest`
- **Returns:** `view('auth.passwords.email')`

#### `sendResetLinkEmail(Request $request)`
- **Route:** `POST /password/email` (name: `password.email`)
- **Middleware:** `guest`
- **Validation:** Manual `$request->validate()` requiring `email` (required, email, exists in `users`). Custom message: “We cannot find a user with that email address.”
- **Processing (development mode – currently active):**
  1. Find the user by email.
  2. Generate a reset token using Laravel’s `Password::createToken($user)`. This token is stored in the `password_reset_tokens` table.
  3. Redirect directly to the password reset form (`password.reset` route) with the token and email as parameters, and a status message indicating the development mode shortcut.
- **Production code (commented out):** Would send the reset link via Laravel’s notification system and return the appropriate status, with logging for both success and failure.
- **Returns:** Redirect.

### `ResetPasswordController` (`App\Http\Controllers\Auth\ResetPasswordController`)

#### `showResetForm(Request $request, $token)`
- **Route:** `GET /password/reset/{token}` (name: `password.reset`)
- **Middleware:** `guest`
- **Returns:** `view('auth.passwords.reset')` with `token` and `email` passed to the view.

#### `reset(Request $request)`
- **Route:** `POST /password/reset` (name: `password.update`)
- **Middleware:** `guest`
- **Validation:** Manual, custom messages:
  - `token` → required.
  - `email` → required, email, exists in `users`.
  - `password` → required, confirmed, `Password::min(8)->letters()->mixedCase()->numbers()->symbols()->uncompromised()`.
- **Processing:**
  1. Call `Password::reset()` with the provided credentials.
  2. Inside the reset callback, force‑fill the new hashed password and a fresh `remember_token`, save the user, fire the `PasswordReset` event, and log the success.
  3. On failure, log a warning with the email and IP, and redirect back with errors.
- **Returns:** Redirect to the login page on success, or back with errors.

## Form Requests

### `LoginRequest` (`App\Http\Requests\Auth\LoginRequest`)

- **Authorization:** `true` (all guests).
- **Rules:**
  - `email`: required, string, email, max:255, exists:users,email.
  - `password`: required, string, `Password::defaults()`.
  - `remember`: nullable, boolean.
- **Custom Messages:** `email.exists` → “These credentials do not match our records.”
- **Data Preparation:** `prepareForValidation()` casts `remember` to a boolean before validation.

### `RegisterRequest` (`App\Http\Requests\Auth\RegisterRequest`)

- **Authorization:** `true`.
- **Rules:**
  - `name`: required, string, max:255, min:3, regex:`/^[a-zA-Z\s]+$/` (alphabetic and spaces only).
  - `email`: required, string, email, max:255, unique:users,email, confirmed (requires `email_confirmation` field).
  - `password`: required, string, confirmed, `Password::min(8)->letters()->mixedCase()->numbers()->symbols()->uncompromised()`.
  - `terms`: required, accepted.
- **Custom Messages:**
  - `name.regex` → “The name must contain only letters and spaces.”
  - `terms.accepted` → “You must agree to the terms and conditions.”
- **Helper Method:**
  - `getUserData()`: Returns the validated data after hashing the password and setting `email_verified_at` to `now()`. This makes every new account immediately verified.

## Middleware

The Authentication module itself does not introduce custom middleware. It relies on Laravel’s built‑in `guest` and `auth` middleware to gate its routes. The Spatie `role` middleware is used elsewhere but not within the auth controllers.

## Routes

**Guest routes (unauthenticated only):**
GET /login → LoginController@showLoginForm (name: login)
POST /login → LoginController@login
GET /register → RegisterController@showRegistrationForm (name: register)
POST /register → RegisterController@register
GET /password/reset → ForgotPasswordController@showLinkRequestForm (name: password.request)
POST /password/email → ForgotPasswordController@sendResetLinkEmail (name: password.email)
GET /password/reset/{token} → ResetPasswordController@showResetForm (name: password.reset)
POST /password/reset → ResetPasswordController@reset (name: password.update)

**Authenticated routes:**
POST /logout → LoginController@logout (name: logout)

All routes are defined inside `routes/web.php` under the `guest` and `auth` middleware groups respectively.

## Integration Points

- **User Model & Ban System:** After successful credential validation, `LoginController` checks `$user->isBanned()`. If the user is banned, the session is immediately destroyed and they are redirected with an error.
- **Spatie Permissions / Roles:** The registration flow assigns the `User` role. This role, together with `Admin`, `Editor`, and `Author`, controls access to admin areas via Spatie’s `role` middleware (not part of this module).
- **Event System:** The `Registered` and `PasswordReset` events are fired but currently have no listeners. They are available for future addition of email notifications or audit logging.
- **Logging:** All critical security actions (failed login, successful login, registration, password reset, logout) are logged using the `Log` facade, aiding in security monitoring and debugging.
- **Password Reset Tokens:** The development flow uses `Password::createToken()` which stores a token in the `password_reset_tokens` table, making the reset link valid without sending an email. The production code path (commented) would use `Password::sendResetLink()` to send a notification.

## Edge Cases & Business Rules

- **Banned users cannot retain a session:** Even with valid credentials, a banned user is immediately logged out and their session invalidated. This check happens *after* the session regeneration, so the original session is completely destroyed.
- **Development password reset shortcut:** The forgot password flow bypasses email delivery entirely. Instead, it generates a token server‑side and redirects directly to the reset form. The token is stored in the database via the standard broker, so it works exactly like a real reset link.
- **Auto‑login after registration:** New users are automatically authenticated without any email verification, because `email_verified_at` is set to `now()` inside `RegisterRequest::getUserData()`.
- **Session security:** Both login and logout explicitly regenerate the CSRF token and invalidate the old session to mitigate session fixation/hijacking.
- **Password complexity:** Enforced on both registration and reset: minimum 8 characters, must contain letters, mixed case, numbers, symbols, and must not appear in known data breaches (`uncompromised`).
- **Rate limiting:** No custom throttling is added in the controllers; the code relies on Laravel’s default rate limiting if configured in `App\Http\Kernel` (not shown in the provided files).
- **Soft‑deleted users are silently filtered:** Because the `User` model uses the `SoftDeletes` trait, all Eloquent queries (including `Auth::attempt()`) automatically exclude users with a non‑null `deleted_at`. Therefore, a soft‑deleted user will receive the “These credentials do not match our records” error even if their password is correct. This is distinct from a banned user (who could still attempt login but gets immediately logged out). Restoration of a soft‑deleted user via `restore()` will allow normal authentication again.

## Technical Debt & Known Issues

These issues stem from the gap between the code and the underlying database schema. They **must** be resolved before the authentication module can function correctly in its current form.

1. **Missing `last_login_at` column**
   - **Where it is used:** `LoginController@login` → `$user->update(['last_login_at' => now()])`; `User::getLastActivityAttribute()` reads it.
   - **Impact:** The schema does not contain this column, so the `update()` call will first throw a `QueryException` (column not found). Even after adding the column via migration, the mass‑assignment will fail because `last_login_at` is not listed in the model’s `$fillable` array (throws `MassAssignmentException`).
   - **Required fix:**
     1. Create a migration that adds `last_login_at` (timestamp, nullable) to the `users` table.
     2. Either add `'last_login_at'` to `$fillable` in the `User` model, **or** replace `$user->update(['last_login_at' => now()])` with `$user->forceFill(['last_login_at' => now()])->save()`. The `forceFill()` approach is often cleaner as it avoids polluting the fillable list for one‑off assignments.

2. **Missing `updated_by` column**
   - **Where it is used:** `User::updater()` relationship (`belongsTo(User::class, 'updated_by')`).
   - **Impact:** Any call to `$user->updater` will fail because the foreign key column does not exist.
   - **Required fix:** Add an `updated_by` column (foreign ID unsigned, nullable, constrained on `users`) via migration, and make it fillable if mass assignment is intended elsewhere. Ensure the column is added before the relationship is used.

3. **Fillable inconsistency**
   - The `User` model’s `$fillable` list does not include `last_login_at` or `updated_by`. After adding the columns, the current code that mass‑assigns `last_login_at` will fail unless the attribute is made fillable or switched to `forceFill()`. See point 1 above.

It is strongly recommended that these items be addressed in the next development cycle and that the corresponding documentation sections be updated to reflect the fixes.
