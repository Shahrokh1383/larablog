
## ساختار کلی پروژه
- **بک‌اند**: یک اپلیکیشن لاراول با جداول، مدل‌ها، کنترلرهای API، پالیسی‌ها و رویدادهای Reverb.
- **فرانت‌اند عمومی**: Next.js (با App Router) که صفحات SSR/SSG را رندر می‌کند و با APIهای لاراول ارتباط برقرار می‌کند.
- **پنل مدیریت**: یک اپلیکیشن React مجزا (مثلاً با Vite) که در یک زیرمسیر قرار می‌گیرد و کاملاً کلاینت‌ساید است. (می‌تواند در همان پوشهٔ Next.js به‌عنوان یک بخش admin-only با lazy load تعبیه شود، اما طبق معمول پروژه‌های حرفه‌ای جداگانه خواهد بود.)

## فاز ۱: اسکلت‌بندی پایه، احراز هویت و نقش‌ها

**هدف:** راه‌اندازی پروژهٔ لاراول، نصب Fortify و Socialite، ایجاد مدل User و جدول نقش‌ها با Spatie، تنظیم OAuth و APIهای Auth. در سمت فرانت، صفحهٔ لاگین، ثبت‌نام، فراموشی رمز و بازیابی پیاده‌سازی می‌شود و قابلیت اتصال با گوگل، فیسبوک و گیت‌هاب فعال می‌گردد. خروجی این فاز یک سیستم احراز هویت کامل API-based است.

**بک‌اند:**
1. ایجاد پروژهٔ لاراول، تنظیم دیتابیس و .env.
2. نصب Laravel Fortify (تنظیم برای SPA/API – فقط مسیرهای Fortify را فعال کنید، views را خاموش کنید).
3. نصب Socialite و پیکربندی درایورهای Google, Facebook, GitHub.
4. نصب Spatie/laravel-permission و اجرای migration آن.
5. ساخت RoleSeeder برای نقش‌های: admin, editor, author, user (guest یک نقش جدولی نیست، بلکه کاربر ثبت‌نام‌نکرده است).
6. اصلاح مدل User برای استفاده از HasRoles.
7. ایجاد کنترلر AuthController با متدهای register, login, logout, forgot-password, reset-password (همه با Fortify) و متدهای redirectToProvider, handleProviderCallback برای Socialite.
8. تعریف Resource برای User برگشتی در API (نام، ایمیل، نقش‌ها).
9. تنظیم CORS برای پذیرش درخواست‌های فرانت‌اند.
10. ایجاد API routes در api.php: `/auth/*` و `/auth/{provider}/redirect`, `/auth/{provider}/callback`.

**فرانت‌اند:**
1. مقداردهی اولیهٔ Next.js و نصب axios یا fetch wrapper.
2. ایجاد صفحهٔ Login با فرم و پشتیبانی از دکمه‌های OAuth.
3. ایجاد صفحهٔ Register.
4. صفحهٔ Forgot Password (دریافت ایمیل) و Reset Password (با توکن).
5. پیاده‌سازی AuthContext برای مدیریت توکن و وضعیت کاربر.
6. تنظیم Middleware در Next.js برای محافظت از صفحات نیازمند لاگین.
7. استفاده از Socialite redirect: کاربر به لینک `/auth/google` ریدایرکت می‌شود، سپس کال‌بک به فرانت‌اند برگشته و توکن را دریافت می‌کند.

**خروجی فاز ۱:** کاربر می‌تواند ثبت‌نام/ورود کند، رمز عبور را بازیابی کند و با شبکه‌های اجتماعی وارد شود. سیستم نقش‌ها در بک‌اند آماده است. تمام درخواست‌ها از طریق API انجام می‌شود.

## فاز ۲: مدل‌های محتوایی (Post, Category, Tag) و پنل مدیریت اولیه

**هدف:** راه‌اندازی بخش مدیریت برای Editor/Admin جهت مدیریت دسته‌بندی‌ها، تگ‌ها و پست‌ها. در فرانت عمومی، هنوز صفحه‌ای ساخته نمی‌شود؛ فقط پنل React آمادهٔ کار با API می‌شود.

**بک‌اند:**
1. ساخت migrations و models برای:
   - Category: name, slug, description
   - Tag: name, slug
   - Post: title, slug, body, excerpt, featured_image, category_id, author_id (user_id), status (draft/published), published_at, views (integer), reading_time (محاسبه ذخیره‌شده یا داینامیک)
   - Pivot: post_tag
2. تعریف روابط: Category hasMany Posts, Tag belongsToMany Posts, Post belongsTo User (author).
3. پیاده‌سازی Policyها با Spatie: فقط admin/editor می‌توانند Category/Tag ایجاد یا ویرایش کنند. نویسنده فقط پست‌های خودش را می‌تواند مدیریت کند. admin همه‌کاره است.
4. ایجاد کنترلرهای API محافظت‌شده با Policy:
   - CategoryController: index, store, update, destroy
   - TagController: index, store, update, destroy
   - PostController: index (فقط مال خودش برای author، همه برای editor/admin)، store, update, destroy
5. برای reading_time: هنگام ذخیرهٔ پست، با استفاده از یک Helper تعداد کلمات بدنه را به دقیقه تبدیل کن (میانگین ۲۰۰ کلمه در دقیقه) و در فیلد reading_time ذخیره کن.
6. API routes محافظت‌شده با sanctum (توکن) و middleware role.

**فرانت‌اند (پنل React):**
1. ایجاد پروژهٔ React (با Vite) در یک پوشهٔ مجزا.
2. نصب React Router، Axios، یک UI kit (مثل Mantine یا Ant Design).
3. ساخت Layout مدیریت با نوار کناری.
4. صفحات:
   - Login (مشترک با سایت یا جداگانه – بهتر است توکن را از سایت عمومی بگیرد، اما می‌تواند مستقیماً به API لاگین کند).
   - داشبورد ساده با آمار اولیه (فعلاً استاتیک).
   - مدیریت دسته‌بندی‌ها: جدول، ایجاد، ویرایش، حذف.
   - مدیریت تگ‌ها: مشابه.
   - مدیریت پست‌ها: جدول با فیلتر بر اساس نویسنده (اگر نقش admin/editor باشد) و فقط پست‌های خودش برای author؛ ایجاد/ویرایش پست (ویرایشگر غنی مانند Tiptap یا Quill)، انتخاب دسته‌بندی و تگ‌ها (با select چندتایی).
5. اتصال API: توکن را از localStorage برمی‌دارد و با axios ارسال می‌کند.

**خروجی فاز ۲:** ادمین، ادیتور و نویسنده می‌توانند از طریق پنل React وارد شوند و محتوای پایه (دسته، تگ، پست) را مدیریت کنند. پست‌ها با دسته‌بندی و تگ‌ها در دیتابیس ذخیره می‌شوند.

## فاز ۳: صفحات عمومی (Home, Authors, Categories, Tags, Post Detail) و APIهای متناظر

**هدف:** زنده‌سازی بخش عمومی وبلاگ با Next.js. صفحات اصلی، پروفایل نویسنده، لیست دسته‌بندی‌ها، تگ‌ها و جزئیات پست به‌صورت SSR/SSG پیاده‌سازی می‌شوند. داده‌ها از APIهای لاراول گرفته می‌شوند.

**بک‌اند (APIهای عمومی):**
1. **Home API**:
   - `/api/home`: برمی‌گرداند:
     - `editors_picks`: ۳ پست که یک فیلد `is_editors_pick` دارند (بعداً ادیتور مشخص می‌کند).
     - `latest_posts`: ۶ پست آخر منتشرشده.
     - `top_categories`: ۷ دسته‌بندی با تعداد پست (می‌تواند بر اساس تعداد پست مرتب شود).
2. **Authors API**:
   - `/api/authors`: لیست کاربران با نقش author, editor, admin. فیلدهای: name, role (شغل مانند Backend Developer که در پروفایل ذخیره می‌شود؟ در ری‌کوئیرمنت شماره ۳، نویسنده یک role مثل Backend developer دارد که جدا از نقش سیستمی است. بنابراین باید فیلد `role` (عنوان شغلی) و `bio` به مدل User اضافه شود. همین‌جا در این فاز انجام دهید. همچنین `social_links` به‌صورت JSON. `avatar`. تعداد کل پست‌ها، مجموع views کل پست‌ها، سال شروع نویسندگی (مثلاً `since` year). کوئری جستجو بر اساس name و role شغلی.
   - `/api/authors/{username}`: پروفایل کامل نویسنده.
3. **Categories API**:
   - `/api/categories`: همهٔ دسته‌بندی‌ها با تعداد پست‌ها (`posts_count`) و تعداد نویسندگان یکتا (`authors_count`). پارامترهای sort: `newest` (بر اساس آخرین پست در آن دسته), `oldest` (اولین پست), `popular` (مجموع views پست‌های آن دسته). برای محاسبهٔ Most popular، باید مجموع views همهٔ پست‌های هر دسته را حساب کنید.
4. **Tags API**:
   - `/api/tags`: همهٔ تگ‌ها با تعداد پست‌ها. پارامتر search?name= برای جستجو. خروجی شامل `popular_tags`: ۷ تگ برتر بر اساس مجموع views پست‌های دارای آن تگ.
   - `/api/tags/{slug}`: جزئیات یک تگ (برای نمایش پست‌های مرتبط با آن تگ، اما در صفحه تگ، نیاز به لیست پست‌ها داریم – بهتر است در همین endpoint پست‌های مربوطه paginate شده برگردد).
5. **Posts API**:
   - `/api/posts`: لیست پست‌ها با فیلتر category, tag, author و pagination. فیلدهای ضروری: title, slug, excerpt, featured_image, author (name, avatar), category (name, slug), tags, created_at, reading_time, comments_count, views.
   - `/api/posts/{slug}`: جزئیات کامل پست شامل body, related_posts (بر اساس اشتراک تگ، محدود به ۴-۵ تا), author info کامل, comments (برای کامنت‌ها فاز بعد).
6. **مدیریت saved posts**: جدول `post_user` (pivot) با فیلد `saved_at` ایجاد شود. APIهای مربوطه در فاز بعد با احراز هویت؛ فعلاً برای API عمومی نیازی نیست.

**فرانت‌اند (Next.js):**
1. تبدیل صفحات HTML/CSS/JS نمونه به کامپوننت‌های Next.js  (مطابق طرح اصلی).
2. **Home Page** (`/`): از `getServerSideProps` یا fetch در سرور کامپوننت استفاده کنید تا داده‌های Home API را دریافت کند. کامپوننت‌های: Hero با Editor's Picks، Latest Posts grid، Topics (دسته‌بندی‌ها) نمایش داده شود.
3. **Authors Page** (`/authors`): لیست نویسندگان با جستجو (کلاینت‌ساید یا با query param). لینک به `/author/[username]`.
4. **Author Profile** (`/author/[username]`): نمایش اطلاعات کامل، لیست پست‌های نویسنده.
5. **Categories Page** (`/categories`): کارت‌های دسته‌بندی با تعداد پست و نویسنده، فیلترهای مرتب‌سازی (newest, oldest, popular) با پارامترهای URL.
6. **Tags Page** (`/tags`): لیست تگ‌ها با جستجو، بخش Popular Tags (۷ تگ).
7. **Tag Detail** (`/tag/[slug]`): نمایش پست‌های دارای آن تگ با pagination.
8. **Post Detail** (`/post/[slug]`): نمایش مقاله کامل، author box, related posts. (کامنت‌ها در فاز بعد)
9. تمام صفحات باید لینک‌های مناسب داشته باشند و SEO friendly باشند (meta tags).

**خروجی فاز ۳:** سایت عمومی کاملاً کاربردی است. کاربران می‌توانند پست‌ها را بخوانند، دسته‌ها و تگ‌ها را مرور کنند و پروفایل نویسندگان را ببینند.

## فاز ۴: سیستم کامنت‌دهی بلادرنگ با Reverb و اطلاع‌رسانی

**هدف:** افزودن کامنت‌ها به پست‌ها، مدیریت مهمان/کاربر، ریپلای و نوتیفیکیشن به کاربران هنگام ریپلای. در پنل مدیریت، تعداد کامنت‌های خوانده‌نشده نمایش داده شود.

**بک‌اند:**
1. نصب و راه‌اندازی Laravel Reverb (و اگر نیاز است Echo server).
2. ایجاد مدل Comment: `post_id`, `user_id` (nullable برای مهمان), `parent_id` (برای ریپلای), `author_name`, `author_email`, `author_website` (فقط برای مهمان), `body`, `is_approved` (پیش‌فرض true یا false؟ طبق معمول سیستم بلاگ، کامنت مهمان شاید نیاز به تأیید داشته باشد، ولی در نیازمندی ذکر نشده. برای سادگی، تمام کامنت‌ها مستقیم نمایش داده می‌شوند، ولی در پنل مدیریت می‌توانند مدیریت شوند. بگذارید `approved` پیش‌فرض true با قابلیت تغییر توسط admin).
3. Policy: مهمان می‌تواند کامنت بگذارد (بدون احراز). کاربر لاگین‌شده می‌تواند کامنت بگذارد و ریپلای کند.
4. APIهای کامنت:
   - `GET /api/posts/{post}/comments`: لیست کامنت‌های یک پست به‌صورت درختی (با parent_id) paginated یا همه (برای ریل‌تایم ابتدا همه را بگیریم). همراه با اطلاعات کاربر (اگر کاربر لاگین کرده باشد).
   - `POST /api/posts/{post}/comments`: ذخیرهٔ کامنت. اعتبارسنجی: اگر کاربر لاگین نکرده (guest), فیلدهای name, email الزامی، website اختیاری. اگر لاگین کرده، user_id تنظیم شود.
   - `POST /api/comments/{comment}/reply`: مشابه بالا اما parent_id به کامنت مادر اشاره کند.
5. Broadcast رویداد `CommentCreated` با کانال Reverb. کانال: `post.{postId}` یا عمومی. برای نوتیفیکیشن ریپلای: اگر کاربر لاگین‌کرده صاحب کامنت مادر باشد، یک نوتیفیکیشن (مدل Notification) ساخته و از طریق Reverb روی کانال خصوصی کاربر (private-user.{userId}) ارسال شود. از Laravel Notifications با broadcast استفاده کنید.
6. برای پنل مدیریت: endpoint `GET /api/admin/comments/unread-count`: تعداد کامنت‌هایی که `is_read` (فیلد جدید در جدول comments) false هستند. هنگام دیدن لیست کامنت‌ها در پنل، می‌توانید آن‌ها را read کنید.

**فرانت‌اند (Next.js):**
1. نصب Laravel Echo و socket.io-client.
2. در صفحهٔ Post Detail، کامپوننت CommentSection:
   - دریافت کامنت‌های اولیه از API.
   - نمایش فرم ارسال کامنت. اگر کاربر لاگین نکرده، فیلدهای Name, Email, Website نشان داده شوند.
   - اتصال به Reverb و گوش دادن به رویداد `CommentCreated` روی کانال `post.{postId}`. کامنت جدید را بدون رفرش به لیست اضافه کنید.
   - برای ریپلای: زیر هر کامنت دکمهٔ Reply، فرم ریپلای (با همان منطق مهمان/کاربر).
   - هنگام دریافت رویداد، اگر کاربر لاگین‌کرده و کامنت ریپلای به کامنت او باشد، یک نوتیفیکیشن در UI نشان دهید (می‌توان از toast استفاده کرد). (نیاز به subscribe کانال خصوصی کاربر: `private-user.{userId}` برای دریافت نوتیفیکیشن‌ها در کل سایت؛ در Layout اصلی این اشتراک را برقرار کنید.)
3. نمایش تعداد کامنت‌ها در کارت پست‌ها (با استفاده از comments_count که در API داریم).

**فرانت‌اند (پنل React):**
1. صفحهٔ مدیریت کامنت‌ها: جدول تمام کامنت‌ها با امکان approve/delete.
2. نمایش عدد کامنت‌های خوانده‌نشده در هدر پنل (با polling یا Reverb). می‌توان یک endpoint ساده دریافت و هر ۳۰ ثانیه چک کرد.

**خروجی فاز ۴:** سیستم کامنت‌دهی بلادرنگ کامل. کاربران می‌توانند کامنت بگذارند، ریپلای کنند و نوتیفیکیشن فوری دریافت کنند. پنل مدیریت تعداد کامنت‌های خوانده‌نشده را نشان می‌دهد.

## فاز ۵: داشبورد کاربری و ذخیره‌سازی پست‌ها (Saved Posts)

**هدف:** تکمیل پنل کاربری (User Dashboard) در فرانت‌اند عمومی با بخش‌های Overview, Top Commenter, Saved Posts, Settings. APIهای لازم ساخته شود.

**بک‌اند:**
1. جدول `post_user` برای saved posts از قبل ایجاد شده. اضافه کردن API:
   - `POST /api/posts/{post}/save` (ذخیره)
   - `DELETE /api/posts/{post}/unsave` (حذف)
   - `GET /api/user/saved-posts`: لیست پست‌های ذخیره‌شده با pagination.
2. **User Dashboard Overview API**:
   - `GET /api/user/dashboard`:
     - `recently_read`: نیاز به جدول `user_post_reads` (user_id, post_id, read_at). هر بار که کاربر صفحهٔ یک پست را باز می‌کند (اگر لاگین کرده)، یک رکورد insert شود. محاسبه:
       - `posts_read_this_week`: تعداد reads در هفتهٔ جاری.
       - `total_reading_time`: مجموع `reading_time` پست‌هایی که کاربر خوانده است (join با post).
       - `recently_read`: ۵ پست آخر خوانده‌شده با اطلاعات مختصر.
   - برای Top Commenter: یک query برای رتبه‌بندی کاربران بر اساس تعداد کامنت‌ها (بدون احتساب مهمان). اگر کاربر جز ۱۰ نفر اول باشد، `is_top_commenter = true` برگردانید.
3. **Settings API**:
   - `PUT /api/user/profile`: به‌روزرسانی name, email, bio, website, profile_image. برای آپلود عکس، از یک disk (مثلاً public) استفاده کنید.
   - `GET /api/user`: اطلاعات کاربر لاگین‌شده.
4. آپدیت Policyها برای محافظت از این مسیرها (فقط کاربر لاگین‌شده).

**فرانت‌اند (Next.js):**
1. ایجاد مسیر `/dashboard` محافظت‌شده با Auth.
2. صفحهٔ داشبورد با سایدبار: Overview, Saved Posts, Settings (پروفایل).
3. **Overview**: کارت‌های آمار (پست‌های خوانده‌شده، زمان مطالعه)، لیست Recently Read، نشان Top Commenter در صورت داشتن.
4. **Saved Posts**: لیست پست‌های ذخیره‌شده، هر کدام با دکمهٔ حذف.
5. **Settings**: فرم با فیلدهای نام، ایمیل، بیو، وب‌سایت، آپلود عکس. ارسال به API.
6. در صفحهٔ Post Detail، دکمهٔ Save/Unsave که وضعیت را از API چک می‌کند.
7. پیاده‌سازی ردیابی مطالعه: در صفحهٔ Post، وقتی کاربر لاگین‌کرده است، بعد از لود صفحه یک call به `POST /api/posts/{post}/read` بزنید تا رکورد خواندن ثبت شود (زمان خواندن می‌تواند بعداً پیاده‌سازی شود، فعلاً ساده).

**خروجی فاز ۵:** داشبورد کاربری کامل. کاربر می‌تواند پست‌ها را ذخیره کند، آمار مطالعهٔ خود را ببیند و پروفایل خود را ویرایش کند.

## فاز ۶: Newsletter و صف ارسال ایمیل

**هدف:** پیاده‌سازی عضویت در خبرنامه و ارسال ایمیل بهترین پست‌ها با استفاده از Queue.

**بک‌اند:**
1. ایجاد مدل Subscriber: email, unique, timestamps.
2. API عمومی: `POST /api/subscribe` (ولیدیشن ایمیل). بازگشت پیام موفقیت.
3. ایجاد یک Job `SendBestPostsNewsletter` که لیست بهترین پست‌های هفته (مثلاً بر اساس views در ۷ روز گذشته) را گرفته و برای تمام subscribers ایمیل می‌فرستد. بهتر است یک Command نیز بسازید که هفتگی توسط Scheduler اجرا شود.
4. تنظیم Laravel Queue (database driver) و اجرای worker.
5. تنظیم Mail (SMTP) برای ارسال ایمیل. قالب ایمیل ساده با لیست پست‌ها.
6. صفحهٔ Contact Us:
   - `POST /api/contact`: ولیدیشن name, email, subject (optional), message. یک Mailable ساخته و به آدرس larablog@gmail.com ارسال کند. از Queue استفاده شود تا کاربر معطل نشود.

**فرانت‌اند:**
1. در فوتر سایت، فرم Subscribe با ایمیل. ارسال درخواست به API.
2. صفحهٔ Contact (`/contact`): فرم با فیلدهای موردنیاز، ارسال به API، نمایش پیغام موفقیت.
3. هیچ بخش مدیریتی برای newsletter در پنل فعلاً نیاز نیست؛ می‌توان بعداً اضافه کرد. (نیازمندی فقط ارسال خودکار بهترین پست‌ها بود.)

**خروجی فاز ۶:** سیستم خبرنامه و ایمیل تماس با ما کاملاً عملیاتی. کاربران می‌توانند عضو شوند و ایمیل بهترین پست‌ها را دریافت کنند. ایمیل‌ها از طریق صف ارسال می‌شوند.

## فاز ۷: قابلیت‌های ویژه پست (Editor's Pick، Related Posts، ردیابی مطالعه) و بهینه‌سازی‌ها

**هدف:** تکمیل جزئیات مربوط به پست‌ها که در فازهای قبل ممکن است ناقص مانده باشد و افزودن Editor's Pick و منطق related posts با تگ‌ها.

**بک‌اند:**
1. افزودن فیلد `is_editors_pick` (boolean) به جدول posts. فقط editor و admin بتوانند این فیلد را در پنل تغییر دهند.
2. در API Home، حالا `editors_picks` واقعی برگردد.
3. **Related Posts**: API جزئیات پست، با استفاده از تگ‌های همان پست، پست‌های دیگر را که بیشترین تگ مشترک را دارند (مثلاً حداقل یک تگ مشترک) انتخاب کند، به‌ترتیب تعداد تگ مشترک و سپس جدیدترین. در endpoint `/api/posts/{slug}` لیست `related_posts` قرار گیرد.
4. **Recently Read** ردیابی کامل: حین فراخوانی `POST /api/posts/{post}/read`، علاوه بر ثبت read، اگر کاربر قبلاً این پست را خوانده، read_at را بروزرسانی کنید تا Recently Read درست کار کند. همچنین views پست: هر بار که صفحهٔ پست لود می‌شود (حتی برای مهمان)، یک increment روی فیلد views بزنید. بهتر است یک middleware یا increment در endpoint پست جزئیات انجام دهید؛ ولی توجه کنید که ربات‌ها باعث افزایش کاذب نشوند. می‌توان از session-based debounce استفاده کرد.

**فرانت‌اند:**
1. صفحهٔ Home اکنون Editor's Pickهای واقعی را نمایش می‌دهد.
2. در صفحهٔ Post Detail، بخش Related Posts از API دریافت می‌شود و نمایش داده می‌شود.
3. هنگام لود صفحهٔ Post Detail، یک API call برای ثبت read (برای کاربر لاگین‌کرده) و increment view (برای همه) انجام می‌دهیم.
4. اطمینان از اینکه reading_time درست محاسبه شده و در کارت پست‌ها نمایش داده می‌شود.

**خروجی فاز ۷:** تمام مکانیزم‌های مرتبط با پست کامل شده است. Editor's Pick، پست‌های مرتبط، آمار views و reading time دقیقاً مطابق نیازمندی کار می‌کنند.

## فاز ۸: تکمیل پنل مدیریت (مدیریت Our Team, کامنت‌ها، کاربران) و بهینه‌سازی‌های نهایی

**هدف:** پیاده‌سازی بخش About/Our Team در پنل مدیریت و عمومی، تنظیمات نهایی نقش‌ها، و اطمینان از اینکه همهٔ نیازمندی‌های ادمین پوشش داده شده‌اند.

**بک‌اند:**
1. ایجاد یک مدل/تنظیم برای About page: مثلاً یک جدول `settings` با key-value که `about_team_members` شامل آرایه‌ای از user_id باشد. یا یک مدل اختصاصی. ساده‌ترین: یک ردیف در جدول settings با key='about_team' و value=JSON شامل user_ids.
2. API برای مدیریت:
   - `GET /api/admin/about-team`: برگرداندن اعضای فعلی.
   - `PUT /api/admin/about-team`: دریافت آرایه‌ای از user_ids (admin/editor/author) برای نمایش در تیم. فقط admin دسترسی دارد.
3. API عمومی: `GET /api/about` که لیست اعضای تیم را با اطلاعات پروفایل (name, role, bio, avatar, social_links) برمی‌گرداند.
4. تکمیل پنل کامنت‌ها: امکان approve/unapprove و حذف. endpointهای مربوطه.
5. پنل مدیریت کاربران (برای admin): لیست کاربران، تغییر نقش (با Spatie syncRoles). APIها با Policy admin.

**فرانت‌اند (پنل React):**
1. صفحهٔ About Team: یک selector برای انتخاب کاربران (admin/editor/author) و ذخیره. (مثلاً یک multi-select از کاربران واجد شرایط).
2. صفحهٔ مدیریت کامنت‌ها: جدول با approve/delete.
3. صفحهٔ مدیریت کاربران: جدول کاربران با امکان تغییر نقش (dropdown).

**فرانت‌اند (Next.js):**
1. صفحهٔ About (`/about`): دریافت داده از API و نمایش تیم به‌صورت گرید با عکس و لینک‌ها.

**خروجی فاز ۸:** بخش About کاملاً پویا از پنل مدیریت کنترل می‌شود. تمام ابزارهای مدیریتی موردنیاز پیاده‌سازی شده و پروژه کامل است.
